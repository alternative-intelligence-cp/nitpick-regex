### 1.4 A `fixed` table of `ClassRange`: how it is declared and read, its size in the emission, and its cost

These are the probes of block 0b. Each table's row *k* is `ClassRange{ lo: 70k u32, hi: 70k+35 u32 }`, sorted and
disjoint. Each was built with the harness's flags (`nitpick.toml`'s `[toolchain]`: `llc -O0 -filetype=obj
-relocation-model=static`, `opt -O2 -S`, `llc -O2 …`, `ld.lld -static … npkrt.o`).

- **Declared** as `pub fixed ClassRange[N]:NAME = [ ClassRange{ lo: 65u32, hi: 90u32 }, … ];` in a module that has
  `use "<path>/class_range.npk".ClassRange;`. At 300, 3 000 and 15 000 rows each compiles alone at exit 0, the
  parse sweep's way.
- **Emitted** as `@"npk.<module>.<NAME>" = constant [N x %"npk.class_range.ClassRange"] […]`. The object holds a
  read-only symbol (`R`) of 8·N bytes in `.rodata`: 0x960 (2 400 B) at 300 rows, 0x5dc0 at 3 000 and 0x1d4c0 at
  15 000. So the README's *"read-only memory"* holds at `c9baa9e`.
- **What the compiler holds of it:**
  - an `N` that is not the literal's count is `NITPICK-TYPE-007`, *"this array literal has 2 element(s) and
    `ClassRange[3]` has a fixed length"*;
  - a row past `uint32` is `NITPICK-TYPE-031`;
  - `ClassRange[0] = []` compiles, as `constant [0 x …] [ ]`;
  - nothing else: order, overlap and the surrogates are the check's (PD-188).
- **The spelling.** A C-style hex literal is refused: `0x41u32` is `NITPICK-LEX-003`, *"digit is not valid for this
  base"*, and so are `0x41`, `0x41_u32` and `0x80u32` *(scratch)*. The base is a suffix at `c9baa9e`, and the prefixes
  were removed (`src/frontend/numeric.npk` lines 5–23, read by `git show`). So `041hexu32` compiles, as 65, and
  `010FFFFhexu32` as 1114111, while `041u32hex` is `LEX-003` *(scratch)*. A decimal row, `65u32`, compiles.
- **Read** as `T[i].lo`, `T.len` and `for (int64:i in 1i64...T.len)`. A table goes to a function only as a view of
  itself: a `fixed ClassRange[]` parameter takes `T[0i64...T.len]`. The probes `read300`, `read3000` and `read15000`
  each exit 0 at both legs. Each one's table reads sorted and disjoint, and its binary search through the view finds 70
  and the last row's `hi`, and misses 106 and the value one past that `hi`. `T` passed as itself is `NITPICK-TYPE-007`,
  *"expected `fixed ClassRange[]`, found `ClassRange[300]`"* — four sites in `slice300` — and so is a `ClassRange[]`
  parameter given `T` *(scratch)*.
- **Every importer pays for a table.** A program that imports a table's module and never names the table (`unref300`,
  `unref15000`) still compiles it and carries it, at −O0 and through `opt -O2`. So does a program that imports only
  `{ClassRange}` from an entry that `pub use`s a 15 000-row table: 0.95 s and 927 849 B of IR, the table in its object
  *(scratch)*. Through the real chain, `tests/unit/hir_size.npk` takes 0.76 s and 1 419 984 B of IR in the tree, and
  0.88 s and 1 590 885 B with a 3 000-row table re-exported by `unicode.npk` in a copy of the tree. The table is in
  its IR.
- **A glob re-export works.** `pub use "./tbl300.npk".*;` in an entry re-exports the table, and a program importing
  `{T300}` from that entry reads it, exiting 0 at both legs (`glob`).
- **The cost is linear** over 300 … 15 000 rows: npkc takes 0.25, 0.37 and 0.90 s on a table alone, against 0.24 s for
  a bare program. That is about 0.05 s of compile per 1 000 rows, and about 60 B of IR text and 8 B of `.rodata` per
  row. At 15 000 rows, `llc -O0` takes 0.14 s and the binary is 204 352 B. The compiler's own
  `tests/backend/programs/big_fixed_array.npk` records DEF-1, a compile quadratic in the rows at the 1.5.0 close's
  compiler (281 s and 30.9 GiB at 30 000 rows). Over this range that curve is not seen at `c9baa9e`. **The harness's
  bound is `COMPILE_TIMEOUT = 300` s a compile** (`TOOL_TIMEOUT` 300 s, `RUN_TIMEOUT` 30 s; `harness/build.py:46–48`).
  So a generated file of 15 000 rows compiles in under a second, about three hundred times inside the bound.

workable, but the flat layout keeps one directory and one pattern); **no digests, the version alone**, because a
re-published or truncated file would regenerate other tables under the same header. *Reversal:* the layout is one
constant each in CI's step and the generator, plus `SOURCES`.

**PD-186 — what the generator emits at 0.3.0, and in what form.**

- **Four families, one generated file each, in `src/unicode/`:**
  - `general_category.npk`: one table per General_Category value of `DerivedGeneralCategory.txt`;
  - `script.npk`: one per Script value of `Scripts.txt`, with `Unknown` the codepoints the file does not list;
  - `script_extensions.npk`: one per script, every codepoint whose Script_Extensions holds it. That is its
    `ScriptExtensions.txt` entry's set of short names, mapped through `PropertyValueAliases.txt`, or its Script where
    the file has no entry for it;
  - `binary_property.npk`: one per binary property of `PropList.txt` and `DerivedCoreProperties.txt`. A line that
    carries a value after the property's name is not a binary property, and the generator names any such property in
    its output and emits none for it.
- **What else is read, and when it is emitted.** `PropertyAliases.txt` names the binary properties and is held to
  them. `CaseFolding.txt`'s `C` and `S` entries are parsed and checked here, one codepoint to one, and emitted at 0.3.3.
  The category groups (L, M, …) are 0.3.1's to form.
- **The form of a file.** Its header holds fixed lines only: *"GENERATED by `tools/gen_unicode.py` from the Unicode
  Character Database 18.0.0 — do not edit; `check_tables_regenerate` holds this file to the generator's output"*.
  There is no date, path or time, so two runs on two days write one text. Then come `mod:<basename>;` and
  `use "./class_range.npk".ClassRange;`. Each table has a comment line giving its property, its value, its ranges and
  its codepoints (the sizes 0.3.5 records), then `pub fixed ClassRange[N]:NAME = [ … ];`. Tables are sorted by name,
  and rows ascend.
- **The form of a row.** Every row is `    ClassRange{ lo: <decimal>u32, hi: <decimal>u32 },`. Decimal is the
  spelling measured at `c9baa9e` (§1.4) and named by no landing. Every set has the surrogates removed (C-3), so
  `GC_CS` has zero rows, which compiles (§1.4). Touching and overlapping ranges are merged. A table is therefore a class
  in H-13's normal form (RX-236): a property's table and a normalised class are one shape, and one text per set. Files
  use LF line ends, ASCII and a final newline.
- **The names** are `GC_` plus the value's short alias (`GC_LU`), `SCX_` or `SC_` plus the script's long name
  (`SC_GREEK`), and `BP_` plus the property's long name (`BP_WHITE_SPACE`), each upper-cased. The generator refuses a
  character outside `[A-Z0-9_]` and a name two sets share. So no name is a keyword at `c9baa9e` (§1.7).
- **The entry re-exports each family with one line**, `pub use "./<family>.npk".*;`, measured to re-export at
  `c9baa9e` and to pass `check_layering` (§1.4, §1.5). That is four lines written by hand. One name per line, B-15a's
  rule 3, which the entry's header cites, would be several hundred hand-copied names that only the generator owns, a
  list the regeneration check cannot see. The header is dated, and `version.npk`'s one name stays one line.

*Alternatives declined:* **one file per table**, because it means hundreds of roots in the parse sweep; **one file for
everything**, because a bump's diff would mix every family; **rows in hex**, because although `041hexu32` compiles at
`c9baa9e`, landing 135, past the pin, changes how a numeral's digit run ends, by its heading; **a hex comment on every
row**, because it roughly doubles the bytes; **the entry one name per line**, for the reason above. *Reversal:* a family
moved or renamed is one emitter of the generator, and regenerates in one run, the entry's lines with it.

**PD-187 — `check_tables_regenerate`: the generator run again, and every file it writes compared, both ways.** It
reads the manifest's new `[unicode]` table: `ucd`, `sources`, `generator`, `tables`, `version` and `hand-written`, the
last listing `class_range.npk`, `unicode.npk` and `version.npk`. It verifies the eight against `SHA256SUMS`, runs the
generator into the run's `$TMPDIR`, and then checks three things:

- every file the generator writes, against the committed file of that name, byte for byte, naming the first differing
  line (`src/unicode/<file>:<line>`);
- every file the generator writes that the tree lacks;
- every `.npk` in `src/unicode/` that the generator does not write and the manifest does not name as hand-written.

A missing or differing UCD file is a `FAIL`, never a pass by a check that ran nothing: a zero is a finding, the
harness's RX-145. **Seen to fail:**

- self-check case 5 goes live: its tree has a table one line different from the generator's output, and it is red,
  naming the file and the line;
- a hand-edited table in a copy of the tree, which is the box;
- each of its mutants red: `sizes-only`, `one-way`, `skip-without-ucd` and `first-file-only` (step 3).

*Alternatives declined:* **comparing the tables' digests**, which says that they differ and never where; **regeneration
in CI alone**, because the local run would then trust the committed tables, which is the failure U-2 names; **the
generator checking its own output**, which is an instrument trusting itself. *Reversal:* the check is one function in
`harness/treecheck.py`, and the manifest's table.

**PD-188 — `check_table_invariants`: every committed table read as data, never by the generator.** It reads every
generated file in `src/unicode/` through the harness's lexical reader (`harness/lexical.py`, which reads bytes and
mirrors the compiler's lexer, RX-157). For each `pub fixed ClassRange[N]:NAME = [ … ];` it reads the rows' integer
literals in every spelling the lexer reads. It holds:

- each `lo <= hi`;
- each `hi <= 1114111`, which is U+10FFFF;
- each `lo` above the previous `hi` plus one: sorted, disjoint and merged, PD-186's normal form;
- no row meeting 55296 … 57343, which is U+D800 … U+DFFF (C-3).

Each failure is named by file, line and rule. `N` against the rows is the compiler's, `NITPICK-TYPE-007` (§1.4), so
the check does not repeat it. **Seen to fail:** a new self-check case, 36. Its tree holds five planted tables, each
breaking one rule (`lo > hi`, past U+10FFFF, unsorted, touching, meeting the surrogates), and each is red by its rule.
Each of the check's mutants is red too. `TESTING.md`'s row gains C-3's clause, as the box has it. *Alternatives
declined:* **the compiler's checks alone**, which hold the count and the width and nothing else (§1.4); **a Nitpick unit
reading the tables at run time**, which sees only the tables it imports, so a family added later is unseen until a unit
names it; **the generator asserting its own output**, which is U-2's failure. *Reversal:* one function.

## 6. What will bite

- **A table passed as itself is `NITPICK-TYPE-007`.** Pass `T[0i64...T.len]` (§1.4).
- **Every importer pays for every table**, named or not, at both legs (§1.4). The full run grows with the tables'
  rows, so read the seconds at each step.
- **`0x41` is `NITPICK-LEX-003` at `c9baa9e`.** The base is a suffix (`041hexu32`), and the rows are decimal.
- **`.gitignore`'s `tools/ucd/*.txt` does not see `extracted/`.** The layout is flat (PD-185).
- **A header that varies breaks regeneration on another day.** No date, path or time goes in a header. The output is
  sorted bytewise, with LF line ends.
- **The surrogates**: `GC_CS` has zero rows by C-3, and that is no error at 0.3.0 (§7).
- **An exit status is one byte.** The units' exits stay below 256.
- **DEF-1's quadratic compile** was a property of one compiler. At `c9baa9e` it is linear over 300 … 15 000 rows, and
  a re-pin measures it again (block 0b).
- **`limit` and `in` are keywords, and so are `range` and `result`.** A generator variable is Python's, but a unit's
  local is Nitpick's, so `bound`, `src` and `rng` are the house's spellings.
