# 0.0.0 — the language probes — PLANNED (the execution record is appended as steps land)

> **Scope:** fourteen small Nitpick programs that ask the compiler whether the
> shapes `meta/specs/` depends on are spellable, compilable and correct. No
> library code is written in this subcycle. What it produces is **a verdict per
> probe** and, where a verdict is negative, an amended specification and a
> recorded decision.
>
> **Why first.** `meta/specs/` was written against the language's documentation
> and against a reading of the compiler's source, and the compiler project's
> most expensive finding is that *a construct that parses is not a construct
> that works* — most of its cycle 0.4 was repair, and every repair dated to the
> cycle that had parsed the construct. Two of this library's load-bearing
> shapes (RX-050's offsets-not-slices, and the explicit-stack parser) exist
> *because* of a language rule; the rest are unverified until asked.

---

## 1. Where you are

- Nothing is built. `src/` holds placeholder directories.
- The compiler is at `../../nitpick`, cycle 1.5 (verification), self-hosting
  declared under D-202. Build it per its own `CLAUDE.md`; the artifact these
  probes use is `build/npkc` from `npkg build`, or
  `.internal/quickemit/npkc` from `quickemit.py`, whichever is current.
- There is no `nregex` harness yet. **Probes are run by hand**, one command
  each, and that is deliberate: the harness is 0.0.2 and building it against an
  unverified set of language assumptions is the mistake this subcycle exists to
  avoid.
- The probes live in `tests/probe/` and **stay in the tree permanently**. They
  are a regression suite for the language shapes this library depends on, and
  0.0.2 picks them up as ordinary `program`-stage entries.

---

## 2. The command

For each probe, from the `nregex` tree root, with `NPKC` pointing at the built
compiler:

```
$NPKC tests/probe/NN_name.npk -o /tmp/p.ll \
  && llc -O0 -filetype=obj -relocation-model=static /tmp/p.ll -o /tmp/p.o \
  && ld.lld -static /tmp/p.o ../../nitpick/build/npkrt.o -o /tmp/p \
  && /tmp/p ; echo "exit $?"
```

A probe that is **expected to be refused** stops at the first command, and its
verdict is the diagnostic code and span, recorded verbatim.

**Every probe exits 0 on success and a distinct positive code per assertion it
fails**, in the compiler's own house style, so a failure names itself. `exit 0`
additionally asserts, through D-151, that nothing leaked.

---

## 3. Decisions taken at planning

- **P-1 — a probe is a program, never a library file.** It has its own `main`
  and `failsafe` and imports nothing from `src/`. A probe that needed library
  code would be testing the library, which is what every other cycle is for.
- **P-2 — a refused probe is a *result*, not a failure of the subcycle.** Two
  probes (06's second half, and 09 entirely) are **expected** to be refused,
  and their value is the exact diagnostic. The subcycle fails only if a probe's
  verdict is *undecided* — a crash in the compiler, a hang, or an output nobody
  can read.
- **P-3 — the verdict is recorded before the next probe is written.** Fourteen
  written and then run together is fourteen where the third one's answer would
  have changed the fourth one's design.
- **P-4 — a negative verdict amends `meta/specs/` in the same commit.** Not a
  note to self, not a TODO. The specification is the authority (RX-002) and an
  authority known to be wrong and not corrected is worse than none.
- **P-5 — the probe programs stay.** They become `tests/probe/`'s permanent
  suite, so a compiler change that breaks one of these shapes is caught by
  `nregex`'s own harness rather than by an engine failing mysteriously in 0.8.

## 4. The probes

Each entry: **what it asks**, **the shape**, **why it matters**, and **what a
negative verdict costs**.

### 01 — a large array of POD instruction values

**Asks:** does a `Vec<Inst>` of 100 000 twelve-byte structs fill, read, copy
and clear without trapping, and what does `#size_of<Inst>()` actually report?

```nitpick
struct:Inst = { InstKind:kind; uint32:a; uint32:b; };
```

**Matters because** `Program.insts` is exactly this (`COMPILE.md` C-1) and
`NREGEX_PROGRAM_INSTRUCTIONS` is 100 000. **Assert the size**: a padding
surprise changes the memory budget and the specification's number.

**A negative verdict costs** the program layout, and `COMPILE.md` §1's struct
is re-derived from what the compiler actually lays out.

### 02 — a tagged enum with payloads, in a `pick` and in a `Vec`

```nitpick
enum:HirKind = { Literal(uint32); Class(int32); Repeat(int32, int32); Empty; };
```

**Asks:** destructuring in a `pick`, storing in a `Vec<HirNode>`, comparing,
`#[derive(Eq, Debug)]`, and `#size_of`.

**Matters because** `HirKind`, `InstKind` and `PatternErrorKind` are all this
shape, and `HirNode` lives in an array.

**A negative verdict costs** the HIR and instruction representations:
parallel-field structs instead of payload variants, which is a worse API and a
larger node.

### 03 — `move T:v` into a generic container

**Asks:** does `vec_push`-shaped code work for `T = int32` and for `T` an
owning struct (one holding a `string`), including the container's drop?

**Matters because** `Vec<T>` (RX-006) must hold both: `Vec<Inst>` is POD,
`Vec<GroupInfo>` may own a name.

### 04 — an inherent impl on a generic struct with a mutating pointer receiver

```nitpick
impl:<T>:Vec<T> = {
    func:push2 = NIL(Vec<T>->:self, move T:v) never fails { … };
};
```

**Asks:** does D-171's inherent family impl work, called as `v.push2(x)`?
**Also asks the free-function form**, so the fallback is measured in the same
probe.

**Matters because** the whole of `src/core/` is this shape.

### 05 — an explicit-stack parser, and a refusal instead of a crash

**Asks:** a parser for a nested bracket language driven by an explicit
`Vec<Frame>` rather than by recursion; 250 levels deep succeeds; **10 000
levels deep produces a clean refusal, not a segfault.**

**Matters because** it is `SYNTAX.md` Y-9 and `SAFETY.md` S-18 — the rule that
a pattern's nesting cannot blow the call stack. This probe is the proof that
the explicit-stack approach is both writable and sufficient.

**A negative verdict** — if the explicit stack is awkward enough to be
unwritable — costs a language request, because the alternative (native
recursion with a depth counter) does not close the hazard: the counter is
checked *after* the frame is pushed.

### 06 — offsets, not slices — **the second half expected refused**

**Asks:** first, a function returning `struct:Match = { int64:lo; int64:hi; }`
built from a `uint8[]` parameter — expected **accepted**. Then a function
**returning the `uint8[]` subrange itself** — expected **refused**.

**Matters because** RX-050 is built on that refusal, and the whole API's shape
follows from it. If the second half is *accepted*, RX-050 is over-cautious, a
`Match` could carry a slice, and `API.md` §2 changes.

**Record the diagnostic code and span verbatim either way.**

### 07 — `string_bytes` at the borrow edges

**Asks:** `string_bytes(s)` into a scanner, the slice's `.len` and `.ptr`, and
the four edges the escape analysis governs — passed down (legal), returned
(refused), stored in a struct outliving the call (refused), held across an
`await` (refused).

**Matters because** `RX-054` makes `uint8[]` the primitive and every entry
point takes one. It also maps exactly which of the four the compiler actually
refuses, which is not the same question as which the specification says it
does.

### 08 — a sparse set over two `Vec<int32>`

**Asks:** O(1) insert, membership and clear over 100 000 keys, with the
invariant `dense[sparse[k]] == k` asserted after every operation, and the
uninitialised-`sparse` trick (reading garbage is safe because `dense` is
checked) exercised deliberately.

**Matters because** `SparseSet` is what makes the Pike VM linear
(`ENGINES.md` R-6) and the "read uninitialised memory safely" trick is exactly
the kind of thing a language with definite-assignment analysis (D-010) may
refuse. **If it refuses, the set needs a zeroed `sparse` array**, which costs
an `O(n)` clear and changes the Pike VM's per-byte cost — a real finding.

### 09 — a `comptime` pattern walker — **expected refused**

**Asks:** a `comptime func:` that indexes a pattern string byte by byte and
returns the position of the first `(`.

**Expected to be REFUSED**, and this probe exists to record *how*. Measured at
the compiler's 1.5.0 in `src/frontend/resolve_type.npk`: `fold_expr` has no arm
for an index expression, and `fold_string_builtin` handles exactly four names,
none of which reads a byte.

**Matters because** it is O-N1's evidence. A compile-time-validated pattern
literal — a malformed pattern becoming a *compile error* — is a property no
regex library in any language offers, and the gap is one `fold_expr` arm.

**The verdict to record** is the exact diagnostic: whether it is a clean
"cannot be evaluated at compile time" (`NITPICK-TYPE-025` or its neighbour) or
something less specific. A good diagnostic makes the request easy to argue.

### 10 — what `comptime` *can* do

**Asks:** the boundary from the other side — `string_concat`, `string_equals`,
`string_byte_length`, `string_is_empty`, a counted `loop`, a mutable local, a
nested `comptime func:` call, all inside `comptime(…)`.

**Matters because** a request is stronger when it says what already works. It
also tells us whether a *pattern-length* or *pattern-equality* check is
available at compile time even without indexing, which would be a small but
real win for a future `#regex_len_check` form.

### 11 — a bitset array field

**Asks:** `uint64[4]` as a field of a struct held in a `Vec`, with union,
intersection, complement, `contains` and iteration; and `#size_of` asserted at
32 bytes.

**Matters because** `ByteSet` is this, and a byte class lives inside an
instruction operand table.

### 12 — the prelude `Iterator` trait on a borrowing struct

**Asks:** implementing `Iterator` (`assoc:Item; func:next = Item?(Self->:self);`)
on a struct holding a `Regex->`-shaped borrow, and driving it with `for … in`.

**Matters because** O-A1 depends on the answer: whether `Matches` can implement
the trait at all, given the struct is second-class.

**A negative verdict costs** nothing structural — `matches_next` is the
explicit form and always works — but it settles O-A1 immediately.

### 13 — the verification rungs refuse by name

**Asks:** `prove(x > 0i32);`, a `limit<Rules>` parameter, and a
`requires`/`ensures` contract, each expected to be refused with
`NITPICK-RUNG-001` naming "1.5".

**Matters because** `VERIFICATION.md` P-1 writes every obligation as a comment
in the syntax it will take, and that is only safe if the real syntax is known
to be *inert* — refused loudly rather than parsed as something else. Confirmed
in the source at `src/backend/ir/ir_stmt.npk`; this probe confirms it in
practice.

### 14 — a program at the size bound

**Asks:** a `Vec<Inst>` built to `NREGEX_PROGRAM_INSTRUCTIONS` (100 000),
walked once, freed, exiting 0.

**Matters because** it is the memory and time floor of the whole library, and
because `exit 0` asserts through D-151 that the `wild` block was released on
every path.

## 5. The steps

Each step is one commit.

**Step 1 — the shape probes: 01, 02, 06, 07.** These decide the program and HIR
representations and the whole API's shape. Run them, record verdicts, and if
06's second half is *accepted*, **stop and re-plan** `API.md` §2 before writing
another probe.

**Step 2 — the algorithm probes: 05, 08, 11, 14.** These decide whether the
parser and the Pike VM are writable as specified. 08's uninitialised-`sparse`
question is the one most likely to produce a real finding.

**Step 3 — the dispatch and generic probes: 03, 04, 12.**

**Step 4 — the compile-time probes: 09, 10, 13.** Expected refusals, run last
because their verdicts change nothing about what gets built — only what gets
asked of the compiler.

**Step 5 — the record and the amendments.** Every verdict written into §7;
every consequence written into `meta/specs/` and `meta/DECISIONS.md`;
`tests/probe/README.md` written, saying what the directory is for and that a
probe is never deleted.

## 6. What the executor should know

- **The reserved words will bite immediately.** `range`, `end`, `in`, `limit`,
  `any`, `buffer`, `raw`, `move`, `error`, `on` — `specs/BUILD.md` §7 is the
  list. A probe about a bitset wants a local called `range`; a probe about a
  match wants `end`. Neither is available; use `rng` and `hi`.
- **`discard(x);` takes parentheses. `defer { … }` takes no trailing
  semicolon.** Declarations end `};`; control-flow blocks do not.
- **Adjacent string literals do not concatenate.**
- **A file's `mod:` name must equal its basename**, or the loader reports
  `NITPICK-RESOLVE-005` at line 1 and says nothing about the name.
- **`raw` is licensed only on a `never fails` callee** (D-163). An `async`
  callee is never `never fails`, so `raw await f()` is unspellable.
- **Strings are move-only** (TYPE-046). Build a name per use rather than
  holding one binding across lines.
- **A `failsafe` must name every reachable error** (REACH-002), including the
  system ones the program's own machinery can raise. Copy the arm set from
  `../../nitpick/tests/backend/programs/proc_tool.npk` and prune.
- **Exit 0 means "and nothing leaked"** (D-151). Every probe exits 0 on success
  on purpose.
- **`llc` and `ld.lld` must be the pinned 20.1.2.** `llvm-config --version`.
