### 1.3 `error` is a keyword; `PatternError` sealed (PD-16)

- `mod:error;` is `NITPICK-RESOLVE-012` at 1:1: *"file `error.npk` declares `mod:;`
  first"* — `error` is a `TypeKeyword` (`LEXICAL_REFERENCE.md` §4). A module named
  `pattern_error` declaring a function `pattern_error`, a struct `PatternError` and an
  enum `PatternErrorKind`, re-exported one name per line, compiles and runs.
- A tag-only enum of thirty-seven, one per line under comment headings; an
  exhaustive `pick` over it with no `(*)`; `k =>! PatternErrorKind` for its tags —
  all compile and run. Adding a kind makes the `pick` non-exhaustive,
  `NITPICK-PICK-001`; swapping two makes the unit exit 20; dropping one leaves an arm
  naming no variant, and the file is refused — **but by the emitter,
  `NITPICK-EMIT-002`, whose own text calls it a defect in the compiler**: the frontend
  accepts a `pick` arm naming a variant the enum does not have (block 2b; reduced in
  §6).
- **Every field `sealed`**: a `PatternError{ … }` literal outside the module is
  `NITPICK-TYPE-079`, four times at the literal, one per field; with the seals
  deleted it compiles (block 2b). Reads — `e.offset`, `e?.offset`, `pick (e.kind)`
  — compile anywhere. `#size_of<PatternError>()` is 32 (S-9's order: 8 of padding).
- A negative `offset` or `span_len` stops on `vec_oob`: 94 at both legs; with the
  guard deleted, 0 — a wrong position reaches the caller.
- `pattern_error.npk` imports `core` for `vec_oob`, so a consumer owes `core`'s
  eleven arms. A function answering `PatternError?` — `pass NIL`, `pass raw
  pattern_error(…)` — is tested with `== NIL`, read with `??` and `?.`, measured.

### 1.7 The loops — the compiler's DEF-127 … DEF-130, and this tree's exposure

At `c970483` four loop shapes give a silent wrong count (the workbench registry,
2026-09-26): a `for` over a range ending at its type's maximum, or over an unsigned
range crossing the sign bit, runs zero times; `loop` and `till` widen an unsigned
bound by its sign; `till` with a negative limit counts down; a `for` binding that
shares an outer local's name overwrites that local. **This tree has none**: no

and `loan_spellings.npk`'s binding `x` is in `run` while its local `x` is in
`consume`. **Every loop this plan writes is a `while` over an `int64`, with
`decreases` the bytes or items left** — the cursor's scan `decreases pat.len -
c.pos`, the units' counters `decreases 100i64 - i`. No design here needs another
shape.

## 3. Steps, in order

**Each step ends green and is one commit.** A step's blocks apply its text, measure
it at the pin and at the control, run the controls that show each claim against a
wrong world, run the full harness, and stage exactly the step's files; the worker
then commits them (§3's commit lines), with the dispatch's `ATTRIBUTION` lines at the
end of the message. **Nothing is pushed until step 6.** The plan file — its title
`RUNNING (<date>)`, then its execution record — is committed in the record commit,
not in a step's.

**The order is load-bearing in three places:** step 1 comes before the layer entry
gains its first `pub use` (step 2); each of steps 3 to 5 appends to the entry
after the one before; step 6 corrects prose the earlier steps made false, and its
counts are read from step 5's run.

## 4. What will bite

- **The pattern's owner must not be written while a cursor holds its view.** At
  `c970483` the compiler does not refuse it and the cursor reads freed memory — 170,
  silently (§1.4). `src/` never holds the owner; a test that builds a `string`,
  takes `string_bytes`, and later reassigns it while a cursor is live is a
  use-after-free with a green-looking exit. The next re-pin refuses it,
  `NITPICK-BORROW-015`.
- **Loops are `while` loops over an `int64`, `decreases` what is left** — never a
  `for` over a range, a `loop` or a `till` (§1.7): at `c970483` each can run the
  wrong number of times at no diagnostic (the compiler's DEF-127 … DEF-130). If a
  design seems to need one, that is a question for the author, not a workaround.
