## Why a subcycle of its own, and why here

**Decided at planning: item 13 is `0.0.4c`, after the adoption and before the
close — not folded into 0.0.4b.**

- **The adoption is mechanical and this is design.** 0.0.4b's acceptance is
  "compiles at the new pin and nothing else changed", which a verifier can
  check by construction. This subcycle changes what a CONSUMER may write — four
  fields refuse a write, one refuses a read, a struct literal is refused — adds
  an arm every `core` consumer owes, and narrows a decision (RX-127) and two
  specification rules. Mixed into one commit, a reviewer cannot tell a clause
  from a contract change, and a revert of one reverts both.
- **Before the close**, because the dispatch says so and because the close's
  triage reads this tree: the third audit's BL-5 remedy may add a `Vec` verb,
  and it should be written against the sealed `Vec`, not re-written after it.
- *Declined — item 13 inside 0.0.4b:* the two reasons above.
- *Declined — after the close, or in cycle 0.1:* the parser is `Vec`'s first
  real consumer; sealing under it would be the one line of that diff nobody
  reviews as a surface change.

**`SparseSet.count` under `ListLen` is the planner's addition to item 13, and it
is flagged as such.** The board named `Vec`'s `count`/`cap` and `Bytes`' `len`
for the limit. `SparseSet.count` is the same kind of field — a count of live
members, written in one module, never meaningfully negative — and the arm it
would add is already owed by every `SparseSet` consumer through `vec.npk`
(measured: the `sparseset.npk` bill is 10 with or without it). So it costs
nothing and closes the same class of defect (§1's BL-3 measurement).

## 1. What was measured — the facts this plan rests on

**The three declarations, exactly as they compile at `c3bdae2`:**

```nitpick
pub struct:Vec<T> = {
    hidden wild T->:items;                 // WILD, DELIBERATELY. See the header.
    sealed limit<ListLen> int64:count;     // elements in use
    sealed limit<ListLen> int64:cap;       // elements the block can hold
};

pub struct:Bytes = {
    sealed buffer:buf;                   // MANAGED, owning, dropped at scope exit. Capacity is `buf.len`.
    sealed limit<ListLen> int64:len;     // bytes in use. NEVER `buf.len`, which is the capacity.
};

pub struct:SparseSet = {
    sealed Vec<int32>:dense;               // the members, in insertion order; the first `count` are live
    sealed Vec<int32>:sparse;              // key -> its position in `dense`, meaningful only below `count`
    sealed limit<ListLen> int64:count;     // live members
};
```

- **The order is `sealed limit<R> T:f`.** `limit<ListLen> sealed int64:count`
  is `NITPICK-PARSE-001`, *"expected a type"*, at the column of `sealed` —
  measured by `nitpick-time`'s planner and confirmed by the compiler seat, whose
  `TYPE_REFERENCE.md` §9.1.2 example is wrong and is corrected in its next docs
  landing. *If `PARSE-001 expected a type` appears at a field, the `limit<…>`
  is in front of `sealed`.*
- **`ListLen` resolves with no import** (the prelude's `pub Rules<int64>`,
  D-308 §6). Its rule `{ $ >= 0i64, $ <= 140737488355328i64 }` admits the
  vacant value 0, so `TYPE-077` is satisfied — and `vec_free`'s deliberate
  poison, `cap = 0`, is a legal value, so RX-139's guard is unaffected.
- **No field this plan limits has its address taken** (`TYPE-063` would refuse
  it): every `Vec`/`Bytes`/`SparseSet` function takes the struct through a
  pointer and writes the field through it, which is a write point, not an
  address.
- **The whole tree compiles with the three declarations**, and the only new
  refusal is `REACH-002` for `LimitViolated` — in **34 roots**, every file in
  `tests/unit/` except `byteset_unit.npk` (the one unit that imports neither
  `vec.npk` nor `bytes.npk`). No probe (probes import nothing from `src/`), and
  not `tests/conformance/import.npk` (`lib.npk` does not reach `core`).

**What a CONSUMER can and cannot do afterwards — each a program run at
`c3bdae2`:**

```
v.count = 3i64;                      NITPICK-TYPE-079   (sealed: written only inside `vec`)
v.cap = 8i64;                        NITPICK-TYPE-079
int64:x = v.items[0i64];             NITPICK-TYPE-080   (hidden: not even read outside `vec`)
Vec{ items: …, count: …, cap: … }    NITPICK-TYPE-079 x2 + TYPE-080  (a consumer's struct literal)
b.len = 2i64;                        NITPICK-TYPE-079
b.buf = buffer_new(8i64);            NITPICK-TYPE-079
Bytes{ buf: …, len: … }              NITPICK-TYPE-079 x2
s.count = 1i64;                      NITPICK-TYPE-079
vec_push(@s.dense, 5i32)             NITPICK-TYPE-079   (the ADDRESS of a sealed field is a write)
v.count, v.cap, b.len, b.buf.len,    compile and run -- a sealed field is READ anywhere
s.count, s.dense.count, vec_get(s.sparse, k)
```

**What the seal does NOT close — measured, and stated rather than left to be
found:**

- **`b.buf.ptr[0i64] = 65u8;` compiles and runs** from a consumer. A write
  THROUGH a sealed field's pointer is not a write of the field. So the accessor
  rule S-23 states for `Bytes` stays this library's (`check_accessor_confinement`
  over `src/`), and a consumer who indexes `b.buf.ptr` has opted out, exactly as
  before. `hidden buf` would close it, at the cost of an accessor for the eight
  test lines that read `b.buf.len` — declined here because item 13 is decided
  design; §6 names it as a candidate for the author.
- **`Vec<int64>:w = v;` compiles** — a header copy, `hidden` and `sealed` fields
  and all. The third audit's N-15 (a double free through a copied header exits
  95) is therefore **not** closed by this subcycle; the close owns it.

**The evidence the decision rests on — and it answers RX-127's *"a bad trade"*
with this cycle's own worst defect.** BL-3 (the second audit) was `vec_oob`
returning for `i == 0`, after which `vec_remove` on an empty `Vec` left
`count == -1` and corrupted the container silently. Planted back into
`vec_oob` (its old body, `discard(guard[i]);`), measured with
`tests/unit/vec_oob_remove_empty.npk`:

```
BL-3 planted, WITHOUT the limit (0.0.4b's end state)   exit 60 -- the unit's "shipped tree's actual exit"
BL-3 planted, WITH sealed limit<ListLen> count         exit 109 -- LimitViolated, AT THE BAD WRITE
```

So the field limit is a second net under the library's own stop: a count that
goes wrong traps where it goes wrong, whatever the stop above it does. RX-127
declined `limit` on the ACCESSORS' PARAMETERS, charging every consumer for a
bound `vec_get` already checks by hand; this limits the COUNTS, which nothing
checked, and the defect it catches is one this repository shipped.

**The arm bills** (`0.0.4b.md` step 11's `bills`): `vec.npk`, `bytes.npk` and
`sparseset.npk` **9 → 10**, `core.npk` **10 → 11** — `LimitViolated`, and
nothing else; `byteset.npk` 10, `limits.npk`, `lib.npk`, `api.npk` 6,
unchanged. **S-8's promise is untouched today** (`lib.npk` does not reach
`core`); the cycle that makes `api` reach `core` inherits eleven identities, and
O-B3 is where that becomes a rule.
