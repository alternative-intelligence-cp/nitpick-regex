A2. THE CAUSE, COUNTED IN THE EMITTED IR.
    LLVM requires a `declare` for a function that is called and not defined.
    npkc emits neither for @npk_failsafe; a program's own `failsafe` supplies
    the `define`, and a library file has nothing to supply it.

                                      src/lib.npk   import.npk (a program)
    call sites to @npk_failsafe             7             7
    `declare` of it                         0             0
    `define` of it                          0             1
    `define i32 @main`                      0             1

    npkc's usage line offers no library or module mode:
$ $NPKC --help
  unknown argument: --help
  usage: npkc <root.npk> [-o out.ll] [--obligations DIR] [--elide nitpick.obligations] [--extra-picky=no-wildx]
  -> exit 2

    CORRECTED 2026-09-04. This line was committed as `-> exit 1` and the number
    was WRONG. Re-run twice here against the same npkc, sha256 matched against
    SHA256SUMS first: exit 2 both times. The two output lines above are
    unchanged and were always right, and A2's point is untouched — `--help` is
    simply not a recognised flag, so the usage line is what npkc prints when it
    cannot proceed. Nothing else in this file cited this number.
    2 IS NOT A REFUSAL. It is the ARGUMENT error, and the difference is a
    harness's problem the moment rule B-6 says to assert on exit codes. The
    alphabet is §F.

WHY THIS IS IN A LIBRARY'S TRANSCRIPT. `BUILD.md` rule B-6 says to assert on
codes and exit codes and never on message text, which is right, and which means
0.0.2's harness will compare integers. A harness that reads "nonzero" as
"refused" scores a mistyped command line as a conformance result, and a
rejection test expecting 1 that gets 2 has not been refused — it has not been
COMPILED. The A2 line above is the small version of exactly that confusion, and
it survived a commit.
