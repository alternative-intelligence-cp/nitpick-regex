The compiler intends the 1/2 split rather than tolerating it: its own cycle
1.5.0 plan, P-20, specifies "an unknown argument exiting 2 with the usage".

WHY THIS IS IN A LIBRARY'S TRANSCRIPT. `BUILD.md` rule B-6 says to assert on
codes and exit codes and never on message text, which is right, and which means
0.0.2's harness will compare integers. A harness that reads "nonzero" as
"refused" scores a mistyped command line as a conformance result, and a
rejection test expecting 1 that gets 2 has not been refused — it has not been
COMPILED. The A2 line above is the small version of exactly that confusion, and
it survived a commit.

AND THE SHARPER HALF, WHICH IS WHAT THE CORRECTION ABOVE BOUGHT. A missing
import exits 1 — THE VERY CODE A REJECTION FIXTURE EXPECTS. So a rejection test
whose fixture path is typo'd, or whose file is later moved, PASSES FOR THE WRONG
REASON: it wanted a refusal, it got a refusal, and the refusal was about the
path rather than about the thing under test. Nothing anywhere reports it. Exit 1
alone cannot tell "refused for the reason this test is about" from "the file was
not there", so A REJECTION FIXTURE MUST ASSERT THE DIAGNOSTIC CODE AS WELL AS
THE EXIT CODE. This library imports by relative path (B-15, P-8) until O-G3
closes, so moved and mistyped paths are the ORDINARY case here, not the exotic
one.

`BUILD.md` ALREADY CARRIES THE RULE THAT CLOSES THIS — rule B-7 (D-237): the set
of codes a rejection test reports must EQUAL the set its expectations name. The
false claim's real cost would have been to point 0.0.2's harness author at the
exit code alone, in the one place where B-7 is what makes the trap unreachable.
0.0.2 implements B-7 as a load-bearing check and not as a nicety.
